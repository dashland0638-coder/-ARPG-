## Proposed Protocol Change

要約（採用案 = Option A。D-1 で確定）:

1. **Implementation persistence gate**: `TESTING → REVIEWING` の条件に「承認範囲の成果物を作業ブランチへ commit・push し、Review Handoff を提示した」を追加する
2. **Review Handoff**: Reviewer への入力を branch + SHA + 差分範囲で固定する（§5 に1か所だけ定義し、agents 側は参照）
3. **Target verification**: Reviewer はレビュー前に SHA の取得可否と成果物の存在を確認し、確認できなければレビューしない
4. **Review persistence gate**: `REVIEWING → DONE` の条件に「review report と Status 更新が push 済み」「Reviewed SHA が最終実装 SHA と一致」を追加する
5. **Push authority の明示**: push は Human Approval 欄に明記された場合だけ許可される。暗黙の許可は無い

### Commit / push option の評価

| 案 | 信頼性 | 再現性 | 既存ワークフローとの整合 | 評価 |
| --- | --- | --- | --- | --- |
| **A** commit + push を REVIEWING 前に必須 | remote 実行環境・別の人間・同一セッションすべてで成立 | SHA で対象固定。後から第三者が同じ対象を取得可能 | §4「残してから渡す」§15「GitHub 上で受け渡す」の具体化。F-13「検証前に push しない」とも両立（push はテスト後） | **推奨** |
| **B** commit のみ、共有 repo なら push 不要 | 現行の実行環境（コンテナ非共有、FACT 17）では MAGE-002 がそのまま再発 | commit があれば SHA 固定は可能だが remote に無い | 「共有か」の判定を Agent に委ねる | 不採用 |
| **C** Reviewer が独立な時だけ push | 同一セッション兼務では remote に何も残らず、後から Review 対象を検証できない | 兼務時は不可 | 「独立か」の判定分岐が増え、§5 の兼務 Review（人間の差分確認を推奨）で人間が差分を取得できない | 不採用 |
| **D** A を基本とし兼務時は commit のみ | C と同じ欠点が兼務時に残る。規則が長くなる | 兼務時は不可 | 例外規定が必要 | 不採用（D-1 で人間が選ぶ場合の代替案として残す） |

A の追加コストは兼務時の push 1回のみ。push 先は作業ブランチであり `main` ではない（§6 の承認範囲外へ出ない）。

## State Transition

**新しい Status は作らない。** 永続化は既存遷移の **条件（gate）** として表す。

```
IMPLEMENTING → TESTING → REVIEWING → DONE          （状態列は現行どおり）
                        ▲ gate P1     ▲ gate P2
```

| 遷移 | 現行条件（§7） | 追加条件 |
| --- | --- | --- |
| `TESTING → REVIEWING` | 全て成功 | **P1**: 承認範囲の成果物（コード・テスト・Task の Implementation Result と Status 更新・その承認単位の analysis）を1つの commit 群として作業ブランチへ push し、Review Handoff を提示した |
| `REVIEWING → DONE` | PASS | **P2**: DONE Gate（下記）をすべて満たす |

P1 を満たせない場合（Persistence 不許可、権限、ネットワーク）:

- `REVIEWING` にしない。`TESTING` のまま止まり、理由を人間へ報告する
- 人間の判断待ちが続く場合は既存の `BLOCKED`（理由: Review Handoff 未完了）を使う（§7「任意の状態 → BLOCKED」）

「IMPLEMENTATION PERSISTED」「REVIEW PERSISTED」を Status にしない理由: どちらも次の遷移の前提条件であり、
独立した作業状態（担当者が作業している状態）ではない。Status を増やすと §7 の表・§7.1 / §7.2 の Work Item 表・
既存 Task の読み替えがすべて波及する。

`REVIEWING` の Status 行を含むコミット自身の SHA はそのファイルに書けない（書くと SHA が変わる）。
そのため **Implementation SHA は Task ファイルには書かず、Review Handoff（会話）と review report の Review Target に書く**。
Task の Status History の `TESTING → REVIEWING` 行には Branch だけを書く。

## Review Handoff

§5 に1か所だけ定義する（implementer.md / reviewer.md は参照のみ。`AGENTS.md` 冒頭「同じルールを他のファイルへ書き写さない」）。

最小項目:

| 項目 | 必須 | 内容 | 理由 |
| --- | --- | --- | --- |
| Target | 必須 | Task ID（Work Item を持つ Task は `<ID> / T-n`） | 承認単位の特定 |
| Branch | 必須 | push 先の作業ブランチ名 | fetch 先 |
| Implementation SHA | 必須 | push 済みの最終実装コミット（40桁） | レビュー対象の固定 |
| Diff range | 必須 | `<base-sha>..<implementation-sha>`（1コミットなら `<sha>^..<sha>`） | 複数コミット・同一ブランチに複数 Task が積まれる運用（U-4）で、差分範囲を一意にする |
| Task file | 必須 | `.ai/tasks/<ID>.md`（Work Item は `<ID>-<ITEM>.md` も） | Approval・Plan・AC・Files To Change・Implementation Result・Test Report・Analysis へのリンクがすべてここにある |

**渡さない（冗長）項目**:

| 項目 | 理由 |
| --- | --- |
| Approved Plan の場所 | Task file に含まれる |
| Analyzer report の場所 | Task file 冒頭の `Analysis:` 行（Task Template）にある |
| Implementation / Test Report の場所 | Task file 末尾の Implementation Result（implementer.md） |
| Changed Files | Diff range から機械的に得られる。Implementation Result の Changed Files との照合は Review Checklist #2 で行う |
| Test Scope | Test Report に含まれる（§14） |

例（MAGE-002 に当てはめた場合）:

```text
Review Handoff
- Target: MAGE-002
- Branch: claude/chapter-structure-scenario-test-q6oj4l
- Implementation SHA: 88fb6fc924bb5f7120401480a3874d45efd3c08b
- Diff range: 88fb6fc^..88fb6fc
- Task file: .ai/tasks/MAGE-002.md
```

## Implementer Responsibilities

implementer.md 手順4を次の2手順に置き換える（文案。確定文言は Implementation 時）:

4. テスト完了後、Human Approval 欄の Persistence が「許可」の場合だけ、承認範囲の成果物を commit し承認欄の Branch へ push する。
   Status を `REVIEWING` にする変更と Status History 行（Note に Branch）も同じ commit 群に含める。
   Persistence が「許可」でない・push できない場合は `TESTING` のまま止まり、人間に報告する（§7 P1）
5. push 済みであることを確認し（`git ls-remote` 等で remote の branch 先端に Implementation SHA が含まれる）、Review Handoff（§5）を出力する

制約:

- テスト完了前に push しない（T-1 F-13 を維持）
- push 先は承認欄の Branch だけ。`main` や他ブランチへ push しない。force push しない
- Files To Change 外のファイルを commit に含めない

Output Template の末尾に `### Review Handoff`（§5 の5項目）を追加する。ただし SHA は自己参照になるため、
Task file には Branch / Diff range の base までを書き、Implementation SHA は会話の Handoff にのみ書く
（Implementation 時にどちらか1形式に統一する。推奨: Task file には書かず会話のみ、正本は review report の Review Target）。

## Reviewer Responsibilities

### Target Verification（Review Order の 0番目として追加）

レビュー内容に入る前に、Handoff に対して次をすべて確認する:

| # | 確認 | 例 |
| --- | --- | --- |
| V-1 | Branch が remote に存在する | `git fetch origin <branch>` |
| V-2 | Implementation SHA が commit として存在する | `git cat-file -e <sha>^{commit}` |
| V-3 | SHA が Branch から到達可能 | `git merge-base --is-ancestor <sha> origin/<branch>` |
| V-4 | Diff range が空でなく、SHA が range の終点 | `git diff --stat <range>` |
| V-5 | SHA 時点の Task file に Human Approval（チェック済み）・Status `REVIEWING`・Implementation Result（Test Report を含む）がある | `git show <sha>:<task file>` |
| V-6 | SHA 時点に Task file の `Analysis:` が指す report が存在する | `git show <sha>:<analysis>` |

レビューは **Implementation SHA の内容** に対して行う。ブランチ先端・自分の working tree・未 commit 変更は対象にしない。

### 確認できない場合の扱い（既存用語のみ）

- `PASS` / `CHANGES_REQUIRED` を出さない（どちらも実装内容に対する判定であり、MAGE-002 F-01 / F-02 のような受け渡し不備を実装指摘として混ぜない）
- review report を作らず、会話で人間へ「**BLOCKED（理由: Review Handoff 不備）**」と、満たせなかった V-n を報告して止まる
- Reviewer は Task file の Status を変更しない（SHA が取得できない場合、書き込む対象の Task file 自体が確定しないため）。
  人間または Implementer が Handoff を再提示するか、必要なら Task を `BLOCKED` に記録する

## Reviewer Report Persistence

- Reviewer の Permission「READ ONLY」を次のとおり定義し直す: **コード・テスト・Task の計画本文・Approval 欄を変更しない**。
  書いてよいのは次の2つだけ:
  1. `.ai/reports/<ID>-review.md`（Work Item は `<ID>-<ITEM>-review.md`）
  2. 対象 Task file の `Status:` 行と Status History への1行追記（§7 で `REVIEWING` の担当は Reviewer）
- Reviewer はこの2つを **1コミット** にして、Handoff の Branch へ push する（Human Approval 欄の Persistence が許可している場合。D-2 / D-3）
- Review commit は Implementation SHA の子孫になる。`git diff <Reviewed SHA>..<review commit>` が上記2種類のファイル変更だけであることが、
  「レビュー後に実装が変わっていない」ことの機械的な証跡になる（MAGE-002 の `88fb6fc` → `4d7662f` と同じ形）
- PASS / CHANGES_REQUIRED の正本は push 済み review report の `Result` 欄。会話上の判定だけでは有効としない（D-3）
- push できない場合: Status は `REVIEWING` のまま、report 内容を会話で人間へ渡し、永続化されるまで DONE にしない

## DONE Gate

`REVIEWING → DONE`（§7 P2）の条件:

| # | 条件 | 採否 | 理由 |
| --- | --- | --- | --- |
| G-1 | 実装完了 | 含意 | TESTING / REVIEWING を経ている時点で成立。独立条件にしない |
| G-2 | 必要なテストが Test Report に記録されている | 含意 | 現行 §14 と Checklist #4〜6 で Reviewer が確認済み |
| G-3 | Reviewer の Result が PASS | **必須** | 現行どおり |
| G-4 | Reviewed SHA が最終実装 SHA と一致（Reviewed SHA 以降の commit が review report と Task の Status 行のみ） | **必須** | AC-6。CHANGES_REQUIRED 後の再実装は新しい Handoff と新しい Review Target を要する |
| G-5 | review report が remote の Branch に存在する | **必須** | AC-5 |
| G-6 | 未解決の BLOCKER / MAJOR が無い | 含意 | PASS の定義（Required Changes: None）に含まれる。独立条件にしない |
| G-7 | 完了についての Human Approval | **不要** | 現行 §7 は `REVIEWING → DONE` を Reviewer 担当としており、完了承認を要求していない。追加すると状態機械の変更になる。人間の統制は実装承認（§6）と push 許可（Persistence 行）で保つ |
| — | Full Regression | **不要** | §14 は Targeted を許容し、DC-3 は未決のまま。P-9 はこれを変えない（AC-8） |

DONE の記録は G-5 と同じ review commit で行う（Status 行と Status History 行）。

## Human Approval

（設計: Question 4 への回答）

**現行の解釈**: §6 の Human Approval は「その承認単位の Files To Change の範囲を実装してよい」ことだけを許可する。
commit / push について §6 は何も書いておらず、承認から push 許可を導く根拠は無い（P-9-analysis FACT 2）。
したがって **暗黙の push 許可は存在しない** と明記する。

**提案**: Approval 欄に Persistence 行を1行追加し、人間が明示的に選ぶ。

```markdown
## Human Approval
- [ ] Approved
- Approved by / date / where:
- Scope of approval:
- Persistence: 許可しない / 許可（branch: <作業ブランチ名>。テスト完了後の commit・push と、Reviewer の review report・Status の commit・push に限る）
```

§6 に追記する文言（文案）:

> Human Approval は、明記された範囲の実装だけを許可する。commit / push は Approval 欄の `Persistence` が `許可` で、
> ブランチ名が書かれている場合に限り、そのブランチへ、テスト完了後に行ってよい。`main` への push、force push、
> 承認範囲外のファイルの commit は、Persistence が許可でも許可されない。
> `Persistence` が空欄・`許可しない` の場合、Implementer は `TESTING` で止まり、push の GO を人間に求める（§7 P1）。
> AI は Persistence を自分で `許可` にしない。

効果:

- 「AI は自律的に push してよい」という読み方をさせない（許可は人間が branch 名つきで書いた場合だけ）
- MAGE-002 の「自動 commit・push はしない」は `Persistence: 許可しない` と同義として読める。その場合でも Protocol 上は
  「未 commit で REVIEWING に進む」ことが禁止されるため、MAGE-002 の失敗（EV-1）は起きない（TESTING で止まって GO を求める）
