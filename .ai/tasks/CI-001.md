## Goal

現在 GitHub Actions CI が継続的に失敗している原因を調査し、UI-002-D を含む既存開発への Regression を避けながら、CI を安定して PASS できる状態にする。一度 PASS させるのではなく、再発しにくい CI 状態を Goal とする（Human、2026-10-02）。

## 原因（Analysis の要約）

- E2E が実時間で待つのに対し、ゲーム内の時間は描画の速さ（GPU の無い CI では SwiftShader で 2〜5fps）× 50ms の頭打ちで決まり、CI の機械の速さ（2 vCPU・混雑）によって run ごとに変わる。2 CPU に制限したローカルで CI の失敗をほぼ同じ顔ぶれで再現（67 件中 23 FAIL）
- 描画が CPU を使い切り、ページの応答・起動も遅れて 45 秒の test timeout を超える
- workflow に `concurrency` が無く、push ごとに 1.5〜3 時間の run が並ぶ。失敗時の結果が残らない

## Analysis の追補（計画中の実測、2026-10-02）

Analysis §5 (a) の「遅いフレームのぶんシミュレーションを分割して実時間へ追いつかせる」は**採用しない**。2 CPU で試した結果、`air-actions`（上昇区間 0.31 秒の中で攻撃を出す）が即座に FAIL した。1 フレームの間（125ms 以上）にゲーム内の時間が丸ごと進むため、Playwright の入力の間隔（数百 ms）の間にゲーム内の時間が進みすぎ、入力のタイミングを要する spec が成り立たない。既存の E2E は「ヘッドレスではゲーム内の時間が実時間の 1/3〜1/5」という前提で書かれている（各 spec の注記）。

代わりに、**ゲーム内の時間と実時間の比を自動テストでは 1/4 に固定する**。描画が 5fps 以上なら機械の速さに関係なく同じ比になる。描画の解像度を半分にして（`deviceScaleFactor: 0.5`）、2 CPU でも 7〜8fps を確保する（下の実測）。

- `mansion-escort:126` は、ゲーム内 0.5 秒に 1 回しか書き換わらないデバッグ表示を、決め打ちの 2.5 秒（実時間）の後に 1 回だけ読んでいた（古い値を読む）。条件が満たされるまで読み直す形に直す（assertion は同じ）

## Implementation Result

### 計画の更新（実装中、Agent 裁量。Goal の範囲内）
- **Analysis の訂正**: リポジトリは public（`list_repos`）で、GitHub の `ubuntu-latest` は 4 vCPU。それでも CI の所要時間・落ちる顔ぶれは、ローカルを 2 CPU に制限した時と同じかそれより遅い（例: コア集合 15 spec がローカル 4 CPU で 45 分・1 FAIL、2 CPU で 1.2 時間・23 FAIL、CI は全 216 件で 1.4〜2.9 時間・1〜19 FAIL）。「CI は 2 vCPU」ではなく「CI の実効速度はローカルの 2 CPU 相当以下で、run ごとに変わる」と読み替える。ローカルの検証は 2 CPU（`taskset -c 0-1`）を CI 相当として行う
- **E2E 全体（2 CPU）で見つかった、時間の基準を固定したことで表に出た待ち方の問題**（変更前の 2 CPU では、ゲーム内の時間がさらに遅く（0.14 倍）たまたま通っていた）。いずれも assertion を弱めず、状態に同期する形へ直す:
  - `tests/combat-events-layout.spec.js`（UI-002-D WI-D6 / D7 の spec）
    - `walkToSmith`: インタラクトが出た瞬間（範囲 3m の縁）で止めていたため、止まるまでの滑りで範囲の外へ出ることがあった → 出たらもう 1 歩入り、止まってから出ていることを確かめる（WI-D7 の 2 件がこれで FAIL していた）
    - WI-D6 の処刑の位置: 最後のダメージ数値の位置（当たった時点）と比べていた → 同じフレームの HP バー（毎フレーム敵の位置）と比べる。剣士の薙ぎ払いは訓練場の藁人形にも当たるため、HP バーが出ている敵のどれかの上であること（以前の比較は別の敵の数値を拾うことがあった）
  - `tests/mansion-lord.spec.js`: 敵情報パネル（毎フレーム書き直し）を間隔を空けて 1 回ずつ読み、短い相（SPLIT）を取りこぼしていた（CI の run #9 でも同じ FAIL）→ ページの中で書き直しのたびに記録し、まとめて読む
- 2 回目の E2E 全体（2 CPU）で、同じ読み方の `mansion-enemies:166`（使用人の予兆 WINDUP を取りこぼす）が FAIL → 記録の仕組みを `tests/helpers.js`（`recordArenaInfo` / `drainArenaInfo` / `arenaInfoValue`）へ移し、同じ読み方をしている `mansion-enemies`・`mansion-butler`・`mansion-warden`・`mansion-lord` の 4 spec で使う
- インタラクトの E2E（WI-D6 の 1 件・WI-D7 の 3 件）は、鍛冶士の作業台（-6.5,12）へ W+D で歩いていた。歩く経路を毎ステップ記録すると、その道は作業台の範囲（3m）の縁（中心から約 2m）をかすめるだけで、家具に当たった時の逸れ方しだいで範囲に入らない run があった（3 回中 1 回は 30 ステップで一度も入らない）→ 対象を店主（0,20）へ変える。W+A でまっすぐ向かい、カウンターに当たって範囲の中で止まる（`mansion-scenario.spec.js` と同じ導線）。検証の中身（対象の上・中央の領域・入力領域を避ける・押している間は動かない・離すと実行）は同じ。変更前（WI-D7 前の src）では WI-D7 の 3 件が引き続き FAIL することを確認
