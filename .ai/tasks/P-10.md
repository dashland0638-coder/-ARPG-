## INFERENCE

- **PI-1**（PF-8 / PF-9）: blob 一致は、P-9 の「copied unchanged」を事後に検証できた。C6 の同一性検証は過去の実例に対しても機能する
- **PI-2**（PF-6）: git の author / committer は「誰が push したか」を示さない（AI セッションで作った commit を人間が push した場合も同じ表示になりうる）。
  P10-D1 のどちらを選んでも、Persistence の主体は git メタデータではなく **Handoff に明示記録** する必要がある
- **PI-3**（PF-12 / PF-13）: ファイル名から Task ID を「解析」すると曖昧になる（`P-10-artifact-handoff-analysis.md` は「Task `P-10` の Work Item `artifact-handoff`」とも読める）。
  H-4 / H-5 は「ファイル名を解析する」のではなく「Handoff の Task ID から期待 Path を組み立てて文字列一致を見る」形にすべき
- **PI-4**（PF-14）: Task file は段ごとに書き換わるため、Planner → Implementer では blob の **完全一致** は Implementation SHA 時点では成立しない。
  同一性は「承認済み版（pin）から、Implementer が許される節（Status / Status History / Implementation Result）以外が変わっていない」ことで確認する必要がある
- **PI-5**（I-4 / F-15）: Implementer は Source SHA を「コピー（restore）」するため、Source SHA は Implementation SHA の祖先にならない。
  Source Branch がセッション終了後に削除されると、Reviewer は出所（到達性）を確認できなくなる
- **PI-6**（PF-2 / PF-6、P-10 analysis Risks「実行環境との不一致」）: 実行環境の既定動作（セッションブランチへの commit / push）は Analyzer の READ ONLY と衝突しうる。
  C6 の H-3（Source commit は Path 1件だけ）は、どちらが push したかに関わらず「Analyzer がコード・Protocol を変えていない」ことを検証できる
