## Task
CHARACTER-MOTION-RENEWAL / プレイヤーキャラクターのモーションを、アクションゲームとして魅力的な動作へ刷新するための調査（DEC-035。CHARACTER-VIS-002 の関連課題として Human が追加、独立 Task として扱う）。
今回は調査と計画のみ。モーションの実装は変えない。

## Summary
1. **FACT**: モーションは「関節ピボットの角度をキーフレームで補間する」自前の仕組み（`CLIPS` / `sampleClip` / `applyPose`、`05-rendering-rig.js`）。skinning・外部アニメーションは無い。攻撃の判定・SE・見た目の山は `core/swing-timing.js` 等の「クリップ長に対する割合」で同期している
2. **FACT**: 4職 × 約10種のクリップ（basic / basic2 / altBasic / altBasic2 / skill2 / dash / retreat / spin / barrier / hold ほか）。**コンボの締め（basic4）はスキル2・突進のクリップの流用**、3段目（basic3）は回転斬りの流用（`05:3167-3176`）。スキルと通常攻撃の見た目が重なる
3. **FACT**: 上位職は専用のクリップを持たず、基礎職のクリップを `JOB_ATTACK_TEMPO`（再生速度）・`JOB_SWING_AMPLIFY`（振りの大きさ）・`JOB_SWING_ANTICIPATION`（溜め）の係数で変えるだけ（`05:3518-3540`、`core/swing-timing.js`）
4. **FACT**: **プレイヤーの被弾に体の反応が無い**（ダメージ数字・画面の点滅・SE のみ。`07-ai-combat.js:1850` 付近ほか）。**戦闘不能も倒れる動きが無く**、結果画面へ移る（`triggerPlayerDown`、`12-progression-ui.js:1244`）。キャラクター切り替えはリグを組み直すだけ（`switchProtagonist`、`14-hud-boot.js:1929`）
5. **FACT / INFERENCE**: 歩行は全職共通の歩幅の式（`strideT += 速度 × 2.7`、振り角 = `min(0.62, 0.045 + 0.085 × 速度)`、`13-update-loop.js:1193-1197`）。脚の長さ（BUILD の hipY 1.14〜1.20）を見ない。概算では、速度 6 m/s で足の掃く距離（約 1.27 m）と進む距離（半周期 約 1.16 m）がほぼ合うが、**タッチのアナログ入力で遅く歩くと（2 m/s で 約 0.51 m 対 1.16 m）足が大きく滑る**（INFERENCE: 式からの計算。撮影での確認は未実施）
6. **FACT**: 待機は「休め（非戦闘）」と「戦闘の構え」の2層（`STANCE_RELAXED` / `JOB_RELAXED_STANCE`、`STANCE` / `JOB_IDLE_PROFILE`）。呼吸・重心の揺れ（`core/relaxed-idle.js` / `core/combat-stance.js`）はあるが、CHARACTER-VIS-002 の撮影では**休めの立ち姿が全員「手を体の前で組む」似た姿勢**（CHARACTER-VIS-002 analysis O-5）
7. 影の旅人は専用の型（`core/wanderer-style.js` / `17-wanderer-style.js`、AD-005・DEC-034）で、刷新の参考基準。刷新で壊さない

## 6. ブレンド・遷移の問題（FACT / INFERENCE）
- クリップ同士の遷移は「次のクリップの最初のキーフレーム」へ向かう補間で、前のクリップの終わりの姿勢は考慮されない（INFERENCE: `sampleClip` の作り。コンボの段の間で姿勢が飛ぶ可能性）
- 攻撃の終わり → 構えは `settleBoost`（`core/combat-stance.js:332`）で吸い寄せる。戻りの動きはクリップに無い
- 歩行中の攻撃: 上半身はクリップ、下半身は歩行の式で、混ざり方は `applyCombatPose` の分岐（`05:3650-`）
- 休め ↔ 構え: `relaxCombatBlend` / `relaxStopBlend` のブレンド（CHARACTER-VIS-001 T-1）

## 8. iPhone の描画負荷・フレームレートへの影響（INFERENCE）
- モーションは関節の角度の計算だけで、描画回数・三角形は増えない（CPU の軽い計算）。描画負荷の主因は CHARACTER-VIS-002 analysis §4 の描画回数
- 被弾・戦闘不能でエフェクト（粒子・残像）を足すと描画回数が増える。足す場合は既存のプール（`giveMesh` 等）を使う

## 9. 既存の操作感を壊さないための制約
- 攻撃の判定の実時間・攻撃間隔・コンボの受付・回避の無敵 / 時間 / クールダウン・キャンセル・移動速度・入力を変えない
- 被弾・戦闘不能で入力を止める時間を足さない（DEC-035「不要な硬直を足さない」）
- 影の旅人の型（AD-005・DEC-034）を変えない
- 既存の E2E（`character-motion`・`weapon-stow`・`job-traits`・`base-class-*`・`air-actions`・`execution-*`・`combat-*`・`wanderer-renewal`）が固定している挙動を守る

## 10. 反対意見と代替案
| # | 反対意見 | 検討 |
| --- | --- | --- |
| A-1 | 外部のアニメーション（skinning・glTF のクリップ）へ移すべき | リグはピボットの階層で、メッシュは部品の組み合わせ。skinning への移行は新しいシステム（E-4 相当）で、CHARACTER-VIS-002 の造形とも衝突する。不採用（既存のキーフレーム方式を拡張）|
| A-2 | 全部の動きを一度に作り直す | 判定・時間との同期が崩れたときに原因を切り分けられない。区分ごと（待機 → 歩行 → 攻撃 → …）、職ごとに段階を分ける |
| A-3 | 被弾の反応で硬直を入れると手応えが出る | DEC-035 が「不必要に長い硬直・操作不能を追加しない」。見た目だけの短い反応（上半身のみ、入力は止めない）にする |
| A-4 | 上位職に専用クリップを全部作る | 保守コストが増える。武器の形が違う職（戦騎士・バーサーカー・鷹の目）から、攻撃の主要クリップだけ専用にし、他は基礎職 + 係数のまま |
| A-5 | 歩きと走りを分ける（歩行キー等）| 入力の追加はゲーム仕様の変更（E-1）。速度に応じた姿勢の連続的な変化（現行の式の改善）に留める |
| A-6 | モーションより先に見た目（CHARACTER-VIS-002）を終えるべき | 体格（頭身）が変わると手の届く位置が変わり、クリップの値の調整がやり直しになる。**頭身の確定（CHARACTER-VIS-002 E-1）の後に攻撃クリップへ着手**するのが手戻りが少ない。待機・歩行の式・被弾・戦闘不能は頭身に依存しにくく、先に進められる |
